## 停止并报告的条件

出现以下任一情况，**立即停止**，不要继续施工，输出当前进度与阻塞原因：

1. 在改动任何代码前，`npm run typecheck` 或 `pytest` 已经失败。
2. 数据库连接失败，或后端无法启动。
3. 某个阶段连续三次尝试仍无法通过验收。**「三次」指三个不同的根因都无解，不是同一个根因重试三次。** 如果你已经定位到明确的单点根因（例如某处语法或配置错误），直接修它；修的过程中若暴露出**新的独立**根因，才开始计数。已定位清楚的根因不计入失败次数。

   实例：`build` 失败、报错指向 `src/lib/remote-store.ts` 的 `"use client"` 位置错误，`typecheck` 通过——这是**一个**已定位的根因，正确动作是改那一行，不是把它记三次然后停止。

4. 你需要新增除 `vitest`、`@testing-library/react` 之外的任何依赖。
5. 你发现 Spec 要求修改一个**未列入本文档「范围与缺陷归属」表、也不在硬约束第 4 条命名例外中**的 API 字段。

**以下情况不构成停止条件，按本文档执行即可：**

- 缺陷归属或任务范围与你的预期不符。本文档的「范围与缺陷归属」表与硬约束第 4 条的命名例外已经给出裁决，不需要再确认。
- Spec 中的行号与实际代码有偏移。以实际代码为准，在报告中记录偏差即可。
- 某条验收标准的通过路径需要你自行设计实现方式。这是设计自由度，不是冲突。
- `grep` 待分类清单非空。清单非空是预期结果，你需要做的是分类，不是停止。
- 你已经定位到明确的构建或类型错误。直接修，不要计入失败次数。

不要为了"完成任务"而绕过停止条件，也不要因为可自行裁决的事项而停止。部分完成的诚实报告比全绿但不可信的报告有价值得多；同样，因范围表述不够精确而完全不施工，也偏离了任务目标。
