## 一、总体结论

| 维度 | 评分 | 一句话结论 |
| --- | --- | --- |
| **流程合理性** | **8.0 / 10** | 「候选制 + 版本门禁 + 精准失效传播 + 费用前置」在开源界属于**第一梯队**——调研的 20+ 个开源短剧项目中，只有 1 个项目（wind-comic）做到了同等精度的依赖失效，只有 2 个做了费用前置。但**缺分集、缺口型同步、环境阶段游离、缺自动质检**四项硬缺口，使其只能做「一条短片」而非「一部短剧」。 |
| **交互体验** | **5.5 / 10** | 视觉基调专业、分镜台已达到可交付水准，**但存在大量确定性缺陷**：一个阶段流程断裂、一个空态把用户引回已完成的步骤、导出页布局有 1400px 空洞、界面直接展示 `MiniMax H3` / `mimo-v2.5-tts-voiceclone` / `ffmpeg` / `providerTaskId` / 原始英文报错、14 条任务因缺标签全部显示为"生成任务"。**当前状态是"工程严谨度远高于产品完成度"。** |
| **综合** | **6.8 / 10** | **骨架是商用级的，装修还停在内测。** 最大的问题不是能力不足，而是**缺一层"把工程语言翻译成创作者语言"的翻译层**，以及**4 个没有走完的闭环**。 |

**最核心的一条判断**：这个项目把"工程诚实"直接当成了"对用户诚实"。工程诚实是"不骗自己"（它做得极好：不伪装失败、不伪造对齐、不静默降级）；用户诚实是"用他能懂的话说清结果"。**当前界面缺的正是这层翻译**——而这个缺口造成的用户困惑，已经超过了它带来的信任收益。

## 二、短剧生成流程合理性评估

### 2.1 当前流程的技术还原（实测确认）

主链由 `src/features/Creative.tsx` 编排，实际为 **5 个 tab、3 道强制门禁、1 个游离阶段**：

| 顺序 | 阶段 | 用户要做什么 | 门禁 / 出口 | 证据 |
| --- | --- | --- | --- | --- |
| 1 | `01 故事方案` | 生成/编辑片名、梗概、主题、起承转合、结局、画幅、时长、镜头数、人物初稿 | `确认故事，进入角色 →` | `Creative.tsx:318`；`StoryWorkspace.tsx:370-398` |
| 2 | `02 角色形象与声音` | 逐角色选形象 + 选声音 + 定稿 | `确认角色，进入分镜 →`（要求全部角色已定稿） | `Creative.tsx:324, 605-617` |
| 3 | **`环境素材`（无编号）** | 逐地点保存设定、生成/上传无人环境图、勾选 3 项检查、确认版本 | **页内自确认，无下一步，不推进，不计入进度** | `Creative.tsx:332`；`LocationsWorkspace.tsx:55` |
| 4 | `03 分镜创作` | 生成分镜草案、逐镜编辑、逐镜生成画面与配音、逐镜人工验收 | `确认分镜`（要求 `check_project` 零 issue） | `Creative.tsx:335`；`CreativeStudio.tsx:296-309` |
| 5 | `04 预览与导出` | 批量生成缺失资产、就绪检查、进入导出页 | 跳转 `/export` | `Creative.tsx:345, 955-973` |

**贯穿全链的机制（本项目的真正含金量，均已源码核验）**：

- **候选制**：所有付费结果先进 `Candidate`，`/select` 才生效，选用时重新校验指纹，过期返回 409 `STALE_CANDIDATE`。
- **版本门禁**：每次写请求携带 `expected`，不符返回 409 `STALE_VERSION`；API 侧对项目行加 `SELECT … FOR UPDATE`，版本检查实际串行化。
- **指纹失效传播**（精度惊人）：
  - `image_fingerprint = hash(persona 去掉声音字段, style)` → **改声音不会让画面失效，改风格才失效**；
  - `pending_changes` 只把"在该镜真的说话"的角色算作声音依赖 → **改一个不说话配角的音色，不会让这一镜失效**；
  - 尾帧必须证明 `reference_mode == "shot-first-frame"`，否则 `LAST_FRAME_STALE`；
  - 下一镜首帧从上一镜真实最后 0.05s 抽帧（`video_dependency.py:47-73`），**连续性靠构造保证而非靠祈祷**。
- **费用前置 + 硬上限**：入队时在项目行锁内校验 `COST_HARD_LIMIT_CENTS` 与 `VIDEO_POINTS_HARD_LIMIT`，超额 402。
- **失败不伪装**：**所有创作类任务都不自动重试**付费请求（`execute.py:417-421`），失败直接呈现给用户；`REFERENCE_UNSUPPORTED` 硬失败而非降级成"文生图"（`test_providers.py:24-38` 明确断言"never degrades to text"）。

### 2.2 与公开开源方案的横向对比

**基准说明**：以下所有仓库均经 GitHub REST API 逐个核验存在（`full_name` / star / forks / license / `pushed_at` 全部实测）。**调研同时修正了两个常见误引**：

> ⚠️ **`markthree/Jellyfish` 是 ★1 的空壳**（0 fork，push 2026-03-16），其 README 路线图把"完整分镜编辑、视频生成与预览流程"标为**规划中**，且文件里仍留着 `https://github.com/your-org/jellyfish/issues` 占位符。**真正的项目是 [`Forget-C/Jellyfish`](https://github.com/Forget-C/Jellyfish)（★6,561，Apache-2.0）**，markthree 是其下游拷贝。以它为对标会得出完全错误的结论。
> ⚠️ **`waoowaoo` 已转向且不再是开源**：[`waooAI/waoowaoo`](https://github.com/waooAI/waoowaoo)（★14,346）现为 Elastic License 2.0，"source-available, not OSI-approved"，README 已变成通用图像/视频画布。

**行业共识阶段链**（综合 Jellyfish、huobao、LocalMiniDrama、ArcReel、DramaClaw、BigBanana、LumenX、ViMax、drama-skills 等 9 个项目的交集）：

```
小说/创意 → 分集规划 → 剧本 → 角色/场景/道具抽取 → 一致性定妆资产
→ 分镜脚本 → 关键帧 → 图生视频 → 配音 → 口型同步 → 剪辑 → 字幕 → 合成导出 → 审查
```

| ② 费用 estimate → reserve → cap（含单次审批） | ✅ 有，但当前配置下 TTS/视频单价为 0，**硬上限对这两类实际失效**（§2.4-5） |

| ④ 可测量、可阻断交付的自动质检 | ❌ 无 |
| ⑤ 版本化 take + 免费 dry-run + 一键回滚 | ✅ 候选制 + 免费本地修稿 + 历史快照对比（`HistoryWorkspace`） |

### 2.3 优势（应保留并在对外材料中强调）

1. **候选制 + 版本门禁**：比开源界普遍的"生成即覆盖"安全得多。开源界只有 wind-comic、ViMax、LumenX（批量抽卡）、BigBanana（九宫格）等少数项目有类似模型，且**没有一个做到"尾帧必须证明派生自本镜首帧"这种溯源强度**。
2. **失效传播精确到依赖类型**：改声音只重做音频不动画面，改外貌才重做画面；改不说话配角的音色甚至不影响该镜。**这个颗粒度在调研的全部 20+ 个项目中是最细的**。
3. **费用与硬上限前置 + 行锁串行**：`create_job` 先对项目行 `SELECT … FOR UPDATE`，再校验金额与点数上限。开源界只有 OpenMontage 做到同等或更强。
4. **诚实降级 / 不伪装**：`REFERENCE_UNSUPPORTED` 硬失败而非偷偷换成文生图；视频模型未启用时明确叫"分镜动态预演成片"；字幕时序明确区分"实测推导"与"人工校准"。**业界罕见，值得作为品牌资产。**
5. **音频工程扎实**：逐句 TTS + 句后停顿本地精确插入 + PCM 中间格式避免 MP3 padding 漂移 + loudnorm(I=-16)；音频句级哈希跨镜复用，**避免重复付费**。
6. **后端测试覆盖扎实**：24 个测试文件 4,183 行，覆盖失效传播、重试契约、成本、视频链路、原生导出（`test_creative.py` 608 行、`test_video_pipeline.py` 346 行等）。

### 2.4 不足（按严重度排序）

#### 🔴 P0-1　无分集 / 多集结构 —— 这使它不是"短剧"，而是"短片生成器"
全仓库 `episode|season|分集|集数|series` **零命中**。`Plan` 无剧集概念，1 项目 = 1 部 6–240 秒的影片。
而「分集」是**开源界共识的第一级结构**：LocalMiniDrama 的 8 步表第 1–2 步就是"多集剧本 / 分集管理"；ArcReel 的流水线里"分集与结构化剧本"是独立阶段；drama-skills 有专门的 `-novel-analyze`（episode-split candidates）与 `-develop`（episode map）；ViMax 的 `novel2movie` 显式做 episodic adaptation；wind-comic 甚至为 60–100 集连贯性补了「剧情记忆」。
**唯一提及"剧集"的地方是一句错误提示**，让用户自己手动拆分（`voice_continuity.py:113`）。

#### 🔴 P0-2　环境素材阶段游离于主链之外（已实测复现）
三层证据完全一致：
- **UI 层**：`Creative.tsx:332` 该 tab **没有编号**，与 `01/02/03/04` 并列；
- **逻辑层**：`confirm()` 只处理 `plan`/`cast`/其余→`generation`（`Creative.tsx:224-237`），环境走的是完全不同的端点 `/locations/{id}/confirm`，**永不推进**；
- **计数层**：进度 = `plan_confirmed + cast_confirmed + shots_confirmed` / **3**（`Creative.tsx:290-292`），环境确认**不计入**；
- **实测**：`LocationsWorkspace.tsx` 全文件**没有任何 `onNext`**；Playwright 实测环境 tab 的可见 ActionBar 数量 = **0**，页内"下一步/进入分镜"按钮数量 = **0**。
- **后端印证**：`selected_location_reference` 在 `shot.location_revision` 为空时返回 `None`，此时画面**回落到纯文字描述**（`creative.py:989-990`）；`workflow_readiness` 也完全不包含环境（`creative.py:289-316`）。

**结果**：用户可以花大量精力做完环境素材 → 确认 → **页面毫无反应，进度条不动，也没有任何出口**。这是当前流程最刺眼的断裂。

> **实测截图证据**：`shots/04-studio-locations.png` 底部无操作栏；同一项目在 `02-studio-plan.png` 底部有完整操作栏。

#### 🔴 P0-3　导航编号与进度计数互相矛盾（实测复现）
实测项目「宿舍八卦风暴」：

| 界面元素 | 实际显示 |
| --- | --- |
| 阶段 tab | `01 已确认` / `02 已确认` / **`环境素材 已确认`** / `03 未开始` / `04 结构待就绪` → **3 项已确认** |
| 页头计数 | **`项目进度 · 2/3 阶段已确认`** |

**同一屏同时告诉用户"3 件事已确认"和"3 件里确认了 2 件"，且阶段总数是 5 个。** 三个数字互不相容。
API 实测印证：`plan_confirmed=True, cast_confirmed=True, shots_confirmed=False, locations={dorm_room: True}`。

#### 🟠 P1-4　导出门槛过严，容易卡死
`Export.tsx:637,641`：`确认当前成片完成播放验收` 要求 `playedUrl === activeUrl`，而 `playedUrl` **只在播放覆盖率 ≥95% 时**才被设置（`Export.tsx:221`）。含义是：

- 用户必须**从头到尾不拖动**地看完 95% 的成片，**且**勾满 6 个复选框，**且**素材没有过期，按钮才可用；
- 只要中途拖了进度条、切换了版本、或素材变 stale，`playedUrl` 就被清空，**此前所有播放全部作废**；
- 界面上按钮看起来是"可用"的（只是 disabled 样式偏淡），配文却是"当前版本实际播放覆盖尚未达到 95%；完整播放后再保存质量结论。"——**用户会认为"点了没反应"**。

设计意图（防止不看片就点通过）是**对的**，但实现方式是"惩罚式"的。开源界对同类问题的解法是**记录并展示证据**（wind-comic 的"四维发布就绪门禁 + 口型对齐实测分"），而不是**用覆盖率门槛卡住按钮**。

#### 🟠 P1-5　费用前置在真实配置下失效（实测复现）
`.env.local:147` 实际配置为：

```
COST_UNIT_PRICE_JSON={"llmPerMToken":900,"imagePerCall":120,"ttsPerKChar":0,"videoPerSec":0}
```

`ttsPerKChar = 0`、`videoPerSec = 0` → **TTS 与视频的金额估算恒为 0，`COST_HARD_LIMIT_CENTS=5000` 对这两类开销完全拦不住**。视频仅靠点数上限（250）另作约束，TTS 仅靠 `TTS_MAX_CHARS` 与限流。

**实测弹窗原文**：`范围：给夜晚留一盏灯 · 最多 0 次调用（可复用结果会跳过）。` / **`无法估算：未配置完整价格`** / 按钮仍为可点的 `开始生成候选`。

> 这是**设计一流、落地为零**的典型案例。用户看到的是"最多 0 次调用"这种明显没意义的数字，而项目最引以为豪的"费用前置"卖点当场失效。

> 另注：`estimate_cost` 对视频按 `duration_sec × videoPerSec` 计价，而 Toonflow 公开的真实数据是**一部 2 分钟片 ¥130 中 ¥120 是视频（≈92%）**。也就是说，**唯一真正需要预估的那一项，恰恰是预估不出来的那一项。**

#### 🟠 P1-6　缺自动质检，且界面把"没做"直接说给用户听
全仓库无任何 CV/ASR/embedding 依赖（`cv2|insightface|whisper|ssim|imagehash|perceptual` 零命中）。API 自己声明：`"visualAudit": "人工预览，未实现自动外观一致性审核"`（`creative.py:136`），并且这句话**被渲染到了用户界面上**：

> `Creative.tsx:657`：「结构与资产检查通过。请预览角色外观和表演效果；**本系统未实现自动视觉一致性审核**。」

对照开源界：OpenMontage 渲染后自动跑 ffprobe、抽 4 个位置的黑帧检测、音频静音/削波检测，**不通过就不交付**；wind-comic 有"画面对剧本 / 一致性 / 口型可对齐性 / 口型-音频实测"四维门禁。**"没有"是可以接受的，"把没有写在交付页上"不可以。**

#### 🟡 P1-7　参考图上限 2 与常见剧本形状冲突（配置层，会导致硬阻塞）
`config.py:31` `image_max_references = 2`（`.env.local` 未覆盖）。
一个"2 个角色 + 1 个已确认环境"的镜头需要 **3 张参考图** → 提交前 `REFERENCE_LIMIT` 409（`creative.py:626-630`），worker 内 `REFERENCE_REQUIRED`/`REFERENCE_LIMIT`（`creative.py:963-982`）再次拦截。
**但分镜生成的 prompt 从不约束 cast 数量以适配参考图预算**（`creative.py:816-829`）。结果是：AI 会老老实实生成"双人对白"的分镜，然后**用户永远无法为这一镜生成画面**，且错误信息只说"请减少参考"。

> **这条的严重性被低估了**：它阻塞的正是**双人对白戏——短剧的主体镜头形态**。而且阻塞发生在用户已经付出剧本、角色定妆、分镜生成等大量成本**之后**。修它只需改一个配置值 + 一句 prompt 约束。

#### 🟡 P1-8　三个"看起来能用、其实不能用"的服务端素材
实测 `public/assets/` 目录只有 `director-avatar.png` + `stitch-*.jpg`：

| --- | --- | --- | --- |

#### 🟡 P2-9　转场能力停留在一个 fade
`compose.py:211-212`：`transition == "fade"` 时给**每一镜**加首尾 0.2s 淡入淡出，**不是跨镜 xfade**。README 对此是诚实的（`README.md:186`），但从创作能力看，这条决定了成片"像 PPT"还是"像片子"。

#### 🟡 P2-10　`REFERENCE_UNSUPPORTED` 的 README 描述与代码不符
`README.md:160` 写「参考图接口明确不支持时才**降级**」。实际 `gpt_image.py:50-57` 是**硬失败**，从不回落到 `/v1/images/generations`。测试 `test_providers.py:24-38` 明确断言"never degrades to text"。**代码是对的（不伪装成功），文档是错的。**

#### 🟡 P2-11　成片交付不可再编辑（开源界"最后一公里"的共识解法）
ArcReel 导出**剪映草稿**、openframe 导出 FCPXML/EDL、wind-comic 导出 EDL/FCP7/AAF，都让创作者能在专业 NLE 里继续调节奏、改字幕、换语气。本项目终止于一个锁死的 MP4。**对"专业创作者/工作室"这个目标人群，这是硬伤。**

#### 🟡 P2-12　compose 有超时自杀风险
每次 ffmpeg 调用上限 880s（`media.py:105`），Celery soft limit 920s（`execute.py:486`）。但一次 compose 要跑 **1 次 probe + 每镜 1 次编码 + concat + 终编码 + 封面**。24 镜项目极易被中途 kill，随后 beat 标记为 `failed`，**且没有任何断点续跑**。

#### 🟡 P2-13　失效传播的两处精度损失（与"并列第一"的保留说明）
1. **`dependency_stamp` 是单字段、后写覆盖**：角色戳（`creative.py:329`）与环境戳（`:185`）互相覆盖，同时依赖两者的镜头只保留最后一个。`pending_changes` 仍能兜住，但 `review_fingerprint` / `preview_fingerprint` 会漏报第二个依赖。
2. **旁白音频未钉住模型**：`init_project` 写 `narrator` 时**不带 `model`**（`creative.py:355-359`），运行时回落到实时 `settings.tts_model`（`:532`）；而对白行是在角色 `creative.voice` 里钉死 `model` 的（`routers/creative.py:946`，实测库中为 `"speech-2.8-hd"`）。后果：**改 TTS 模型只让旁白失效，不让人物对白失效**，且 `PATCH /narrator` 与 `init_project` 两条设置路径行为不一致。

### ⚠️ 范围外但建议尽快确认的风险

**无任何身份认证与授权**：`owner_id` 恒为 `"local-user"` 且从不校验（`models/__init__.py:26`）；`/media/{key}` 可读取媒体根目录下任意文件（`routers/media.py:11-26`）。此外 `.env.example` 被 `config.py:13` **当作配置源加载**，其中含明文疑似真实的 DeepSeek / IMAGE / MiniMax 密钥（`.env.example:25,48,80`），而 `.gitignore` 只忽略 `.env`/`.env.local`。
> 本地单机自用可接受；**一旦部署到任何多用户或公网环境，这是最高优先级问题**。建议先确认 `.env.example` 是否已被提交进版本库。

   `LocationsWorkspace.tsx:37-40`：`生成无人环境候选` 与 `上传环境图` 都是 `disabled={dirty}`，旁边只有一条被动 warning「环境设定尚未保存」，**没有"去保存"的可点引导**。更糟的是「保存场景设定」是 `disabled={!dirty}` —— **两个按钮永远只有一个可用**，用户很难建立心智模型。

## 四、具体改进方向

### P0 — 下一迭代必做（直接影响"能不能用"）

**1. 把环境素材焊进主链，统一编号与计数**
- 导航改为 `01 故事 / 02 角色 / 03 环境 / 04 分镜 / 05 导出`（`Creative.tsx:318-350`），去掉游离项；

- 进度改为 `X / 5`，并把 `locations` 纳入 `workflow_readiness`（后端 `creative.py:289-316`）。
- **验收标准**：环境阶段出现与 01/02 一致的底部 ActionBar；确认后 tab 自动前移；页头计数与 tab 显示一致。

**2. 建立"用户语言层"，全量收敛技术术语**
- 新建 `src/features/creative/copy.ts` 文案字典，把 `parent_revision / providerTaskId / entityId / nonce / stale / H3 / ffmpeg / asset_id` 统一映射为业务描述；

- 抽一个统一 `<TechnicalDetails>` 组件，替换 `CandidateList / shared / HistoryWorkspace / CharacterWorkspace` 四处重复实现，**默认折叠、不参与主视觉**；

### P2 — 能力与架构（下一大版本）

**12. 分集结构（最高优先级的新能力）**
- 引入 `Episode` 层：`Project → Episode → Plan → Shot`；
- 参考 drama-skills 的 `-develop`（episode map）与 wind-comic 的「剧情记忆」（第 N 集写手获得前情提要）；这是从"短片工具"变成"短剧平台"的唯一分水岭。

**13. 口型同步路线**
- 短期：在 `ShotReview` 增加「口型偏移」人工标注字段，并在导出页给出对齐提示；
- 中期：接入开源组件（MuseTalk / LatentSync，后者对中文视频更友好）。**注意行业现实：开源口型方案相对视频模型已经落后，且多人同框尚未解决**（需要按发言人裁切）。wind-comic 的做法值得抄：**从视频 prompt 中剥离台词，只让模型生成"口型动作"，再在后期与 TTS 对齐**，并**对做不到的语言/场景诚实跳过**。

**14. 增加自动质检（让"没做"从界面上消失）**
- 最低成本版本：导出后自动 ffprobe + 抽帧黑帧检测 + 音频静音/削波检测，**不通过则不交付**（OpenMontage 模式）；
- 这一步能让 `Creative.tsx:657` 那句"本系统未实现…"体面地删除。

**15. 成片可再编辑**
- 导出剪映草稿 / FCPXML / EDL 之一。这是开源界对"最后一公里"的共识解法（ArcReel 剪映、openframe FCPXML/EDL、wind-comic EDL/FCP7/AAF）。

**16. 修并发与一致性（B12/B13/B14）**
- 让 worker 写入路径也走项目行锁；`dependency_stamp` 改为多依赖集合；`save_location` 只在**影响画面生成**的字段变化时才 `shots_confirmed=False`。

**17. 补前端测试**
- 后端 4,183 行测试 vs 前端 0 行。本报告 §3.5 的 14 个缺陷**全部位于前端**，且**全部可被组件测试捕获**（tab 状态、空态分支、任务标签、封面兜底、警告样式）。这是投入产出比最高的一项工程改进。

**18. 统一设计 token**
- 把 `--cw-gold` 收敛到 `DESIGN.md` 的 `#F5B942`，清理 8 个近似金色；把 `workbench.css` 的 `:has()` 布局劫持（`:881-882`、`:930`）改为组件级状态类。

## 五、一句话总结

**流程骨架已达商用级严谨**——候选制、版本门禁、**全开源界最细的依赖失效传播**、费用前置、失败不伪装，这五点在调研的 20+ 个公开项目里属于第一梯队（依赖失效精度与 wind-comic 并列第一，费用前置与 OpenMontage 同档）。

**但产品完成度停留在内测**：一个阶段流程断裂、一个空态把用户引回已完成的步骤、导出页 60% 是黑屏、14 条任务同名无法辨认、界面直接展示 `MiniMax H3` / `mimo-v2.5-tts-voiceclone` / `ffmpeg` / `Failed to fetch`，以及三个"点了没用"的服务端素材开关。

**下一阶段建议冻结新功能，先做四件事**：
① 把**环境阶段焊进主链**并统一编号/计数；
② 建一层**用户语言翻译层**，把所有 `id / version / provider / stale` 关进「技术详情」；
③ 修掉 §3.5 的 **14 个确定性缺陷**（全部是前端小改，其中 B1/B2/B3/B4 是用户直接可见的硬伤）；
④ 补齐**真实计价配置**，让费用前置这个卖点在真实环境里真的生效。

这四件事做完，体验评分可从 **5.5 提升到 8.0 以上，且几乎不增加新代码风险**。之后再投入分集与口型同步这两个"从短片工具到短剧平台"的能力跃迁。
